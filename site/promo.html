What industry speakers recommend, and how Harness Firmware does it

0:00 / 4:43

The quotes and where they come from

Each quote is an excerpt copied from the talk’s captions and links to the moment it was said. The speakers recommend practices; none of them reviewed or endorsed Harness Firmware. Beside each quote is how Harness Firmware does it.

  1. “Define your guardrails, your agents, your docs, testing policies, really governance just one time”
    Davis Palmie, Factory · The Software Factory: From Bug Report to Production Code, 11:48

    Project rules live in two files that load at the start of every chat: CLAUDE.md for Claude Code and AGENTS.md for Codex. You write them once and stop re-explaining the project.

  2. “Don’t pass everything to the agent.”
    Elizabeth Fuentes Leone, AWS · Why Bigger Context Windows Won’t Save Your Agent, 14:26

    Skills are step-by-step guides. On every turn the agent sees only each skill’s name and description, and a guide’s full text loads when a task uses it, so the project can keep many guides while the context stays small.

  3. “When you join a new company there are a lot of rules that are not really codified anywhere.”
    Tereza Tížková, Factory · What It Actually Takes to Build a Software Factory, 19:29

    When you correct a mistake and its cause is confirmed, the agent writes the lesson to pitfalls.md in the repository without asking. Other project facts go into the reference files with /recall save. Later chats read them and avoid the known mistakes.

  4. “It’s best to be agnostic for everyone.”
    Tereza Tížková, Factory · What It Actually Takes to Build a Software Factory, 5:12

    Claude Code and Codex read the same project notes in .claude/reference, and most skills have a Codex version, so you can switch tools and keep the rules and lessons.

  5. “The danger is that the engineer never noticed that there was a choice to make.”
    Gabriel Martinez, G2i · Generation Is Cheap, Review Is Expensive: How to Stop Shipping AI Slop, 1:00

    In /deep-plan the agent finds the facts and brings each open choice to you with its recommendation. Nothing is built until you pick Go.

  6. “We don’t need a human to be shepherding this agent through every single step”
    Ryan Cooke, WorkOS · No, That’s Not a Software Factory, 8:03

    You start /long-horizon and it saves the plan to a file on disk. A fresh agent does each step and another agent runs checks written before the step; only steps that pass count, and when a chat fills up the work resumes from the file.

  7. “The agents will often overconfidently claim that they did something when in fact they did not do it.”
    Miguel (Browserbase) and Corby (Microsoft) · Your LLM Judge Is a Confident Liar: Building Better Verifiers, 6:50

    In /long-horizon the checks for each step are written before the step runs, and a separate agent runs them without reading the worker’s report. A step counts as done only when its checks pass.

  8. “Side-by-side comparison becomes the next evolution of the eval cycle”
    Hussein, Braintrust · Why Building an Eval Platform Is Harder Than It Looks, 9:52

    In /arena agents build several versions separately, and a judge scores them blind against the same criteria. The strongest version is kept, with the best ideas from the others added to it.

  9. “Expensive things you want to run once when the PR goes up.”
    Dru Knox, Tessl · Harness Engineering: How to Build a Software Factory, 7:23

    Codex reviews every pull request before merge. When you type /merge, confirmed findings are fixed and the whole diff is reviewed again, and the pull request merges only after a clean review and passing CI, at the commit that was reviewed.

  10. “Prompting my agent for the same request over and over again”
    Hussein, Braintrust · Why Building an Eval Platform Is Harder Than It Looks, 16:02

    /refine weekly counts your corrections across a week of chats and pull request comments, and puts rule edits for the repeated ones in one pull request. The rules change only when you merge it.

No talk covered these

  1. Cross-company review

    OpenAI’s Codex reviews pull requests made in Claude Code, and Anthropic’s Claude reviews pull requests made in Codex, so the review can catch what the author’s model misses. You merge the pull request or type /merge (Harness-Firmware #214).

  2. /coordinate

    You name a second Claude Code chat. The two check each other’s claims against the pull request, CI and main until they agree on who does what, and a message from the other chat never counts as your approval.

  3. Codex skill sync

    Each skill has a Codex version or is marked Claude-only, and CI checks this on every push, so a fix to a skill can’t silently skip Codex.
