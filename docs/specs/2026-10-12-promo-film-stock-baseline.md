# Promo film: stock baseline

Researched 2026-10-12 against the official Claude Code docs (code.claude.com/docs, Markdown pages fetched that day), the official Codex docs (learn.chatgpt.com/docs, where developers.openai.com/codex now redirects), OpenAI's own Codex plugin for Claude Code (github.com/openai/codex-plugin-cc), and template `ryanportfolio/Harness-Firmware` at `4c0ddfc`. It maps what a developer already gets from stock Claude Code or Codex under the owner's standard, "better than the average setup, and it ships ready": **strong** means no stock feature gives the outcome, **ready** means stock offers parts a user would have to find and wire up while Harness Firmware ships the mechanism built in and switched on (each ready verdict names those parts), and **none** means stock already does it out of the box, so the film never claims stock cannot do something it can.

## rules

- Stock: Claude Code loads `CLAUDE.md` at the start of every session from managed, user (`~/.claude/CLAUDE.md`), project and local (`CLAUDE.local.md`) scopes, with `@path` imports; "Claude treats them as context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook instead." (https://code.claude.com/docs/en/memory#claude-md-vs-auto-memory)
- Stock: Claude Code reads `AGENTS.md` as the project instructions when no `CLAUDE.md` exists, and a **Project instructions** setting can load both (https://code.claude.com/docs/en/memory#agents-md). Codex "reads `AGENTS.md` files before doing any work", layering `~/.codex/AGENTS.md` with root and nested files (https://learn.chatgpt.com/docs/agent-configuration/agents-md)
- Stock: `.claude/rules/` holds one-topic rule files ("Each file should cover one topic"); a rule with `paths:` frontmatter loads only when Claude reads or edits a matching file; rules can be symlinked across projects (https://code.claude.com/docs/en/memory#path-specific-rules)
- Stock: the docs prescribe the structure: "target under 200 lines per CLAUDE.md file", move multi-step procedures to skills and area-only rules to path-scoped rules, and add a rule when "Claude makes the same mistake a second time" or "A code review catches something Claude should have known about this codebase" (https://code.claude.com/docs/en/memory#write-effective-instructions)
- Stock: `/init` "analyzes your codebase and creates a file with build commands, test instructions, and project conventions it discovers. If a CLAUDE.md already exists, `/init` suggests improvements rather than overwriting it." With `CLAUDE_CODE_NEW_INIT=1` it asks which artifacts to set up (CLAUDE.md files, skills, hooks), "explores your codebase with a subagent, fills in gaps via follow-up questions, and presents a reviewable proposal before writing any files"; it also folds in Cursor, Copilot and (with the variable) `AGENTS.md` rules (https://code.claude.com/docs/en/memory#set-up-a-project-claude-md)
- Stock: Codex `/init` generates an `AGENTS.md` scaffold to review and commit; Claude Code `/import codex` and Codex `/import` carry instruction files, skills and other setup from the other tool (https://learn.chatgpt.com/docs/developer-commands?surface=cli, https://code.claude.com/docs/en/commands)
- Stock: `/doctor` flags checked-in CLAUDE.md content Claude could derive from the code and offers to migrate always-loaded guidance into skills and nested CLAUDE.md files; `/doctor prompt-audit` looks for "instructions written for older models, references to files or commands that don't exist, and files that contradict each other" and proposes edits, changing nothing until asked (https://code.claude.com/docs/en/skills#bundled-skills, https://code.claude.com/docs/en/memory#audit-your-instruction-files)
- Stock: Claude Code Review reads `CLAUDE.md`, flags newly introduced violations as nits, and "if your PR changes code in a way that makes a `CLAUDE.md` statement outdated, Claude flags that the docs need updating too" (Team and Enterprise, research preview) (https://code.claude.com/docs/en/code-review#claude-md)
- Stock: when a project skill named `verify` or `simplify` exists, Claude Code's built-in commit instructions tell Claude to run it right before each commit; `/run-skill-generator` writes the per-project skill that teaches `/run` and `/verify` how to build, launch and drive the app, and `/verify` then uses it (https://code.claude.com/docs/en/skills#run-your-checks-before-each-commit, https://code.claude.com/docs/en/commands)
- Stock: Claude Code ships "built-in instructions for how to write commits and pull requests" plus a git status snapshot in every conversation (https://code.claude.com/docs/en/settings-reference#includegitinstructions)
- Edge: a project kernel that loads in every chat for both tools (template `CLAUDE.md`, template `AGENTS.md`)
- Verdict: none — every Claude Code and Codex user already has this out of the box; it is the shoelaces.
- Edge: the kernel ships a pre-written working agreement, not an empty file. Verification: inspect logs, run scripts and read code before claiming anything works; never claim a visual check you did not perform; when the authoritative check cannot run, flag the risk instead of claiming a pass. Core principles: plan first; reproduce bugs before fixing them; no unrequested refactors, features or abstractions; never hard-code to pass a test and say when a test or requirement is wrong; weighty recommendations get a `/why` pressure test before they are presented. Git: on "Complete" commit, push and open or update the one PR for the branch; squash-merge; never force-push. Review: opening or updating a PR runs the other vendor's review in the same turn. Memory: a confirmed quirk goes to `pitfalls.md` without asking (template `CLAUDE.md` § CRITICAL: Verification, § Core principles, § Git: push on completion, § Codex review on every PR, § Project reference library)
- Verdict: ready — stock parts a user would wire up: writing these rules into their own `CLAUDE.md` (the docs teach exactly this kind of rule, but `/init` writes build commands, test instructions and conventions, not a working agreement), the built-in git instructions, and a `verify` skill made with `/run-skill-generator`. The firmware ships the field-tested set on day one; the review and pitfall rules are scored under cross-vendor and lessons.
- Edge: kernel structure: `CLAUDE.md` holds cross-cutting rules only and says so in its first line; topical facts live in six on-demand reference files indexed by a table; standing rules say new rules must earn their place, stale content gets pruned and nothing the harness already injects is restated (template `CLAUDE.md` § Core principles, § Project reference library; product.md § Layer 1: kernel and token efficiency)
- Verdict: ready — stock parts: the docs' structure advice (under 200 lines, procedures to skills, area rules to `.claude/rules/` with `paths:`), `/doctor` to migrate, `/doctor prompt-audit` and Code Review to catch stale lines. The firmware ships the kernel already split, plus the rule that keeps it that way.
- Edge: `/init-project`, when the user asks for setup, fills the kernel's FILL IN sections from detected facts: what the project is plus a short "won't compromise on" list capped near 10 lines, what this sandbox can verify and which signal is authoritative (CI, deploy log or local tests), and where the app runs plus the install and migration policy; it reuses facts already configured and asks only for consequential facts it cannot detect (template `.claude/skills/init-project/SKILL.md`; template `CLAUDE.md` § What this project is, § CRITICAL: Verification, § Environment & deploy target)
- Verdict: ready — stock parts: `/init` (or interactive `/init` behind `CLAUDE_CODE_NEW_INIT=1`, which also detects, asks about gaps and proposes before writing), prompted by the user to cover verification capability, the authoritative signal and deploy policy, which `/init` does not ask about on its own.
- Edge: what "updates" means, exactly: the setup profiles say "A configured project can receive a requested narrow update"; `/init-project` runs "only when requested" and FILL IN markers "signal unknown facts, not authorization to edit the project". Nothing re-runs setup or rewrites the kernel by itself as the repo changes. The part of the rule set that does grow by itself is `pitfalls.md` (scored under lessons) (template `.claude/skills/init-project/references/profiles.md` § Optional setup profiles and starter cleanup; template `.claude/skills/init-project/SKILL.md`)
- Verdict: none — stock `/init` on an existing CLAUDE.md "suggests improvements rather than overwriting it", and `/doctor prompt-audit` proposes edits to stale instructions. The owner's phrase "automatically adds or updates these rules to be relevant to your repo" overstates the skill: it adds on a setup request and updates only on a further request.
- Edge: `/init-project` also proposes the project's own CI (`write-ci-workflow.mjs`: Node, Python, Rust and Go jobs plus a `firmware` job running the Codex skill sync check), written only after the user approves; it offers a full or minimal skill profile, sets the prose default, strips template-only files and wires the `starter` remote (template `.claude/skills/init-project/references/ci.md`, `profiles.md`)
- Verdict: ready — stock parts: `/install-github-app` writes Claude review and `@claude` workflows but no test CI, and any session writes a test workflow on request; the firmware ships a generator that detects the stacks.

## lessons

- Stock: auto memory is on by default in local sessions; Claude "saves four kinds of notes for itself", including `feedback`: "corrections you give Claude and approaches you confirm", and the first 200 lines or 25KB of `MEMORY.md` load every session (https://code.claude.com/docs/en/memory#auto-memory)
- Stock: auto memory limits: "Claude skips anything it can derive from the codebase, such as architecture, file paths, or debugging fixes", and it lives at `~/.claude/projects/<project>/memory/` on one machine. `autoMemoryDirectory` can be set in project settings to move it, but "The value must be an absolute path or start with `~/`" (https://code.claude.com/docs/en/memory#storage-location)
- Stock: memory files get a `modified` ISO timestamp that "shows how current the fact is, both to you and to Claude"; `/memory` browses and edits them; "add this to CLAUDE.md" writes the committed file instead (https://code.claude.com/docs/en/memory#how-it-works)
- Stock: a subagent with `memory: project` keeps learnings at `.claude/agent-memory/<name-of-agent>/`, "project-specific and shareable via version control"; "`project` is the recommended default scope"; it builds up "codebase patterns, debugging insights, and architectural decisions", and a line in the agent file makes it maintain that memory proactively. The same agent file can run the whole session through `--agent` or the `agent` setting, where its system prompt replaces Claude Code's default (https://code.claude.com/docs/en/sub-agents#enable-persistent-memory, https://code.claude.com/docs/en/sub-agents#invoke-subagents-explicitly)
- Stock: Claude Code Projects (public beta, Pro and Max, not Team or Enterprise) keep project memory of "requirements, decisions, and pitfalls" that every cloud thread reads at start; "Claude saves preferences like these to project memory on its own", and the files are listed under Auto memory "because Claude writes them itself as it works in the project"; a project is "yours alone" (https://code.claude.com/docs/en/claude-projects#give-a-project-standing-context)
- Stock: Codex local memories are opt-in, kept per machine, and the docs say: "Keep required team guidance in `AGENTS.md` or checked-in documentation. Treat memories as a helpful recall layer, not as the only source for rules that must always apply." Codex hooks list "Summarize chats to create persistent memories automatically" as a use (https://learn.chatgpt.com/docs/customization/memories, https://learn.chatgpt.com/docs/hooks)
- Stock: `/doctor prompt-audit` reports outdated or contradictory instructions across CLAUDE.md, rules and skills, changing nothing until asked (https://code.claude.com/docs/en/memory#audit-your-instruction-files)
- Edge: the pitfall rule: when a quirk cost a retry, a backed-out change or a user correction and its cause is confirmed, the agent writes it to the committed `.claude/reference/pitfalls.md` before the task ends, without asking, amending an existing entry over adding one; built-in auto memory is switched off so lessons have one home (template `CLAUDE.md` § Project reference library, § Core principles; template `.claude/skills/recall/SKILL.md`; template `.claude/settings.json`)
- Verdict: ready — committed, shared learned memory exists in stock: a subagent with `memory: project` writes debugging insights into the repo, and Projects memory saves pitfalls on its own (per user, cloud threads, Pro and Max). A user would wire it up by writing a custom agent with `memory: project` and a save instruction, then delegating to it or running the session as it with `--agent` (replacing the default system prompt), or by writing the rule into `CLAUDE.md` themselves. The firmware ships the rule, the file and the trigger (confirmed cause, before the task ends) switched on in the main session, for both tools. It is an agent instruction, not enforced, and committing it follows normal git authorization.
- Edge: `recall` reads only the topic files a task needs and, when a stored fact changes an action, says so with file and date ("per pitfalls.md (2026-03-14): ..."), so a stale fact surfaces as a dated claim the user can correct; it prefers current source when a note conflicts with reality (template `.claude/skills/recall/SKILL.md`)
- Verdict: ready — stock auto memory already loads topic files on demand and stamps each with a `modified` date out of the box (on one machine); what a user would add is the instruction to cite the file and date when a fact changes an action. A detail; not a headline beat.
- Edge: save discipline: every non-pitfall fact needs the user's authorization and must change future decisions, be durable and carry evidence; a contradicted fact is amended in place with a `retired YYYY-MM-DD: <old claim>; reason: <what changed>` line; `memory-audit.mjs` lists never-read files and dated entries older than six months (template `.claude/skills/recall/SKILL.md`; product.md § Layer 2: project memory)
- Verdict: ready — stock parts: `/doctor prompt-audit` for stale or conflicting instructions, auto memory's own index curation and `modified` dates; the save gate, retire line and audit script are what a user would otherwise write.

## two-tools

- Stock: Claude Code reads `AGENTS.md` directly, or a `CLAUDE.md` containing `@AGENTS.md` keeps "the one file every tool shares"; it does not read "anything under a `.agents/` directory" (https://code.claude.com/docs/en/memory#share-one-file-with-other-coding-tools)
- Stock: Codex reads `AGENTS.md` and can be pointed at other names with `project_doc_fallback_filenames` (https://learn.chatgpt.com/docs/agent-configuration/agents-md)
- Stock: each tool's built-in learned memory is its own and local: Claude Code auto memory under `~/.claude/projects/<project>/memory/` (https://code.claude.com/docs/en/memory#storage-location), Codex memories in a per-machine store (https://learn.chatgpt.com/docs/customization/memories)
- Stock: migration exists both ways: Claude Code `/import codex` brings "instruction files, MCP servers, commands, subagents, and skills" once (https://code.claude.com/docs/en/commands); Codex imports Claude Code instruction files, skills, hooks, subagents and "Project memories from Claude Code", and in the ChatGPT desktop app "automatic updates" keep "imported work in sync with the original agent" (one direction, into Codex) (https://learn.chatgpt.com/docs/import)
- Stock: a subagent's `memory: project` folder (`.claude/agent-memory/<name>/`) is a committed directory any tool could be told to read (https://code.claude.com/docs/en/sub-agents#enable-persistent-memory)
- Edge: one shared rule surface with a clean runtime boundary: `AGENTS.md` tells Codex to read only three `CLAUDE.md` sections (project identity, verification, environment) plus the reference files, never to run the Claude hook, to spawn fresh-context subagents, and to call `rtk` explicitly (template `AGENTS.md` § Defaults, § Capabilities, § RTK)
- Verdict: ready — stock parts: Claude reading `AGENTS.md`, or an `@AGENTS.md` import; the user would write the split between shared facts and runtime-specific workflow themselves.
- Edge: one lesson store for both tools: Claude Code and Codex both read and write `.claude/reference/` through `recall`, and both built-in memories are switched off (`autoMemoryEnabled: false`; "Do not use or enable Codex's built-in `memories` feature for project knowledge"), so a lesson either tool learns reaches the other (template `.claude/settings.json`; template `AGENTS.md` § Safety)
- Verdict: ready — no stock feature shares learned memory both ways out of the box, but parts exist: a committed `memory: project` subagent folder plus an `AGENTS.md` line telling Codex to read and write it, or the desktop app's import sync, which carries Claude Code project memories into Codex's local store in one direction only. The firmware ships the shared store and the switch-offs.

## planning

- Stock: plan mode: Claude "reads files, runs shell commands to explore, and writes a plan, but does not edit your source"; edits stay blocked until the user approves; `Ctrl+G` edits the plan; `/plan` enters it (https://code.claude.com/docs/en/permission-modes#analyze-before-you-edit-with-plan-mode)
- Stock: plan files are written to disk, `plansDirectory` chooses where (https://code.claude.com/docs/en/settings-reference#plansdirectory), and after compaction the plan is "Re-injected from disk" (https://code.claude.com/docs/en/context-window#what-survives-compaction)
- Stock: `AskUserQuestion` "asks multiple-choice questions to gather requirements or clarify ambiguity" (https://code.claude.com/docs/en/tools-reference#askuserquestion-tool-behavior), and the best-practices page prescribes "Interview me in detail using the AskUserQuestion tool ... then write a complete spec to SPEC.md" (https://code.claude.com/docs/en/best-practices#let-claude-interview-you)
- Stock: Codex has `/plan`, and its long-running-work guide says "start with `/plan`. Ask ChatGPT to interview you, identify constraints, and turn the result into a goal with measurable success criteria" (https://learn.chatgpt.com/docs/long-running-work)
- Stock: the advisor tool consults a second, stronger Claude model "before committing to an approach"; it receives the full conversation (https://code.claude.com/docs/en/advisor)
- Edge: `deep-plan` interview discipline: rounds of at most 4 questions, recommendation first, ask only where a wrong guess forces rework (low-stakes items become recorded assumptions), never two questions in one round that depend on each other, a depends-on graph where a changed premise voids its descendants, and it never answers a decision for the user (template `.claude/skills/deep-plan/SKILL.md` § Building a round, § Handling answers)
- Verdict: ready — stock parts: plan mode plus an "interview me with AskUserQuestion, then write SPEC.md" prompt, or Codex `/plan` with an interview request; the question discipline is what the user would have to spell out each time.
- Edge: a resumable ledger at `.tmp/deep-plan/<slug>/ledger.md` with stable question IDs, the user's verbatim answers and rejected options, resumed after compaction or in a new session, with a 30-minute ownership check (template `.claude/skills/deep-plan/SKILL.md` § Ledger)
- Verdict: ready — stock plan files already persist and survive compaction out of the box; a record of decisions, verbatim answers and rejected options needs a user-written SPEC.md or decisions-file convention. Persistence alone is not the beat.
- Edge: before the Go gate, the 1 to 3 weightiest decisions go to `why`, one fresh reviewer that never saw the conversation, plus a "what would go wrong if reversed" question; nothing is built until the user picks Go (template `.claude/skills/deep-plan/SKILL.md` § Stop and gate; template `.claude/skills/why/SKILL.md`)
- Verdict: ready — stock plan approval already gates building; stock parts for the second opinion: `/advisor` (which sees the whole conversation) or a reviewer subagent the user briefs by hand.

## long-work

- Stock: "Tasks persist across context compactions", and `CLAUDE_CODE_TASK_LIST_ID` shares one list across sessions (https://code.claude.com/docs/en/interactive-mode#task-list)
- Stock: `/goal` keeps Claude working across turns until a condition holds; Claude Code restores an active goal on every resume route (https://code.claude.com/docs/en/goal#resume-with-an-active-goal). Codex has its own `/goal` Goal mode (https://learn.chatgpt.com/docs/long-running-work)
- Stock: dynamic workflows run a script that orchestrates many subagents, resumable in the same session; with `/effort ultracode` "Claude plans a workflow for each substantive task", and "A single request can turn into several workflows in a row: one to understand the code, one to make the change, and one to verify it" (https://code.claude.com/docs/en/workflows#let-claude-decide-with-ultracode)
- Stock: Projects run "A build or migration bigger than a session" as parallel cloud threads with shared memory and an Overview of what needs you (Pro and Max beta) (https://code.claude.com/docs/en/claude-projects#when-to-use-a-project)
- Stock: after compaction, project-root CLAUDE.md is re-read, the plan-mode plan is "Re-injected from disk", and invoked skills are re-attached within a token budget (https://code.claude.com/docs/en/context-window#what-survives-compaction)
- Edge: `long-horizon` keeps a state file on disk (contract with numbered acceptance checks, versioned amendments that never weaken acceptance, Verified progress, Remaining with depends-on, Dead ends, Method notes, Audit log) and resumes after compaction by reconciling it with the real workspace, asking before taking over a run another session touched in the last 30 minutes (template `.claude/skills/long-horizon/SKILL.md` § State file)
- Verdict: ready — surviving compaction and sessions is stock out of the box (task list, `/goal` resume, plan re-injection); the film must not claim persistence. Stock parts for the rest: a `/goal` condition or a user-written contract file. The firmware ships a contract whose acceptance checks only grow and a progress list that holds only audited results.
- Edge: dead ends and stagnation rules: a failed approach is recorded and not retried without new evidence; the same step failing audit twice forces a new approach; three batches in a row with nothing newly verified force a rewrite of the remaining plan; at max(5, 2 x initial steps) rounds the plan is reassessed (template `.claude/skills/long-horizon/SKILL.md` § Stagnation, § Guardrails)
- Verdict: strong — `/goal` stops only when its evaluator says met or impossible, an unrecoverable error occurs, or Claude makes no tool calls for several turns, and ultracode plans workflows but keeps no list of ruled-out approaches; no stock feature remembers dead ends across rounds or forces a change of approach after repeated failure.
- Edge: parallel rounds, each in its own detached worktree with its own baseline, merged back only when the main file still matches its pre-checkout hash, then one fresh auditor reruns every applied round's check in the main workspace (template `.claude/skills/long-horizon/SKILL.md` § Parallel rounds)
- Verdict: ready — stock parts: `/batch`, workflows and `isolation: worktree` subagents already run parallel units in isolated worktrees; conflict-by-hash and the post-merge recheck are the firmware's additions.

## checking

- Stock: `/goal` "adds a separate evaluator that checks your condition after every turn, so completion is decided by a fresh model rather than the one doing the work", but the evaluator "doesn't run commands or read files independently", judges "what Claude has surfaced in the conversation", and runs on the small fast model (https://code.claude.com/docs/en/goal#how-evaluation-works)
- Stock: Stop hooks live in settings, are fixed before the work starts, and "can run a script for deterministic checks or a prompt for model-evaluated ones" (https://code.claude.com/docs/en/goal); agent-based hooks (`type: "agent"`, experimental) "spawn a subagent that can read files, search code, and use other tools to verify conditions before returning a decision", with up to 50 tool-use turns, for example "Verify that all unit tests pass. Run the test suite" before Claude may stop (https://code.claude.com/docs/en/hooks-guide#agent-based-hooks). The hook's subagent receives the hook input, which includes `last_assistant_message`, Claude's final response (https://code.claude.com/docs/en/hooks#stop-input)
- Stock: Codex Stop hooks run a check when a turn stops and can keep Codex going with `"decision": "block"`; the docs list "Run a custom validation check when a chat turn stops, enforcing standards" (https://learn.chatgpt.com/docs/hooks)
- Stock: the best-practices page prescribes "Before treating a task as done, have a subagent review the diff in a fresh context and report gaps", for example against PLAN.md (https://code.claude.com/docs/en/best-practices#add-an-adversarial-review-step)
- Stock: each subagent "runs in its own context window", and `isolation: worktree` gives it an isolated repository copy (https://code.claude.com/docs/en/sub-agents)
- Stock: workflows can have independent agents adversarially review each other's findings (https://code.claude.com/docs/en/workflows#when-to-use-a-workflow); `/verify` builds and runs the app "rather than relying on tests or type checks" (https://code.claude.com/docs/en/skills#run-and-verify-your-app)
- Stock: the security-guidance plugin sends each turn's diff to "a separate Claude review focused on security" and re-prompts Claude with the findings (https://code.claude.com/docs/en/security-guidance)
- Stock: permission deny rules such as `Edit(tests/**)` block Claude's file tools on chosen paths, and sandboxing restricts shell commands' filesystem access (https://code.claude.com/docs/en/permissions#how-permissions-interact-with-sandboxing)
- Stock: Codex's guide asks you to "Write a goal that lets ChatGPT verify its own progress" (https://learn.chatgpt.com/docs/long-running-work)
- Edge: the `long-horizon` auditor is a fresh subagent whose brief is written per step at Plan, before the executor exists, saved with a recorded sha256 and dispatched unchanged; it never sees the executor's report or narrative, reruns the done-check itself, and treats executor logs as claims (template `.claude/skills/long-horizon/SKILL.md` § Context boundary, § Round loop)
- Verdict: ready — a checker fixed before the work exists in stock: a command Stop hook runs a fixed script, and an agent Stop hook (experimental) runs a fixed prompt that can run tests; a user wires either up in settings. What stock does not give: the agent hook receives Claude's final message, so it is not blind to the worker's account, and one hook prompt covers the whole session rather than a brief written for each step. The firmware ships the per-step, hash-pinned, blind auditor.
- Edge: integrity check by hash: before each round the manager records a content-hash manifest of the workspace; the auditor diffs against it and rates the round `suspect` when the executor touched anything outside its write scope or the tests and gates that judge it ("passing check proves nothing if executor could edit it") (template `.claude/skills/long-horizon/SKILL.md` § Round loop; template `.claude/skills/long-horizon/scripts/manifest.mjs`)
- Verdict: ready — no stock reviewer, evaluator or hook detects that the worker edited the check it is graded by, but a user can prevent it by wiring deny rules on the test and check paths (`Edit(...)`) plus sandbox write restrictions for shell commands. The firmware ships detection for every round over the whole workspace, with no per-path setup.
- Edge: only results that are complete, clean and aligned with the current contract enter Verified progress, and a last fresh auditor reruns every acceptance check on the final workspace because a later round can break an earlier one (template `.claude/skills/long-horizon/SKILL.md` § Completion)
- Verdict: ready — stock parts: a `/goal` condition is judged after every turn (from the transcript), and an agent Stop hook can rerun the test suite before stopping; the firmware ships a final fresh agent that reruns every acceptance check itself.

## attempts

- Stock: `/batch` decomposes a change into 5 to 30 independent units and runs one background subagent per unit in an isolated worktree; each "implements its unit, runs tests, and publishes its change" (https://code.claude.com/docs/en/commands)
- Stock: a fork subagent is the documented choice "when you want to try several approaches in parallel from the same starting point" (https://code.claude.com/docs/en/sub-agents#fork-the-current-conversation); `/branch` and `/fork` try another direction in a copy of the conversation (https://code.claude.com/docs/en/commands)
- Stock: workflows can "draft a plan from several angles and weigh them against each other" (https://code.claude.com/docs/en/workflows#when-to-use-a-workflow); agent teams (experimental, off by default) run "competing hypotheses" where teammates "try to disprove each other's theories" (https://code.claude.com/docs/en/agent-teams)
