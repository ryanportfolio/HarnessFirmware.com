# Promo film: stock baseline

Researched 2026-10-12 against the official Claude Code docs (code.claude.com/docs, Markdown pages fetched that day) and the official Codex docs (learn.chatgpt.com/docs, where developers.openai.com/codex now redirects), and against template `ryanportfolio/Harness-Firmware` at `4c0ddfc`. It maps what a developer already gets from stock Claude Code or Codex, so the promo film claims only the Harness Firmware edges that survive that comparison; "strong" means no stock feature or documented stock pattern gives a typical user the same outcome.

## rules

- Stock: Claude Code loads `CLAUDE.md` at the start of every session from managed, user (`~/.claude/CLAUDE.md`), project and local (`CLAUDE.local.md`) scopes, with `@path` imports; "Claude treats them as context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook instead." (https://code.claude.com/docs/en/memory#claude-md-vs-auto-memory)
- Stock: Claude Code reads `AGENTS.md` as the project instructions when no `CLAUDE.md` exists (v2.1.277+), and a **Project instructions** setting can load both (https://code.claude.com/docs/en/memory#agents-md). Codex "reads `AGENTS.md` files before doing any work", layering `~/.codex/AGENTS.md` with root and nested files (https://learn.chatgpt.com/docs/agent-configuration/agents-md)
- Stock: `.claude/rules/` holds one-topic rule files ("Each file should cover one topic"); a rule with `paths:` frontmatter loads only when Claude reads or edits a matching file; rules can be symlinked across projects (https://code.claude.com/docs/en/memory#path-specific-rules)
- Stock: the docs prescribe the structure: "target under 200 lines per CLAUDE.md file", move multi-step procedures to skills and area-only rules to path-scoped rules, and add a rule when "Claude makes the same mistake a second time" or "A code review catches something Claude should have known" (https://code.claude.com/docs/en/memory#write-effective-instructions)
- Stock: `/init` "analyzes your codebase and creates a file with build commands, test instructions, and project conventions it discovers. If a CLAUDE.md already exists, `/init` suggests improvements rather than overwriting it." With `CLAUDE_CODE_NEW_INIT=1` it asks which artifacts to set up (CLAUDE.md files, skills, hooks), "explores your codebase with a subagent, fills in gaps via follow-up questions, and presents a reviewable proposal before writing any files"; it also folds in Cursor, Copilot and (with the variable) `AGENTS.md` rules (https://code.claude.com/docs/en/memory#set-up-a-project-claude-md)
- Stock: Codex `/init` generates an `AGENTS.md` scaffold to review and commit; Claude Code `/import codex` and Codex `/import` carry instruction files, skills and other setup from the other tool (https://learn.chatgpt.com/docs/developer-commands?surface=cli, https://code.claude.com/docs/en/commands)
- Stock: `/doctor` flags checked-in CLAUDE.md content Claude could derive from the code and offers to migrate always-loaded guidance into skills and nested CLAUDE.md files; `/doctor prompt-audit` finds outdated, broken or contradictory instructions and proposes edits (https://code.claude.com/docs/en/skills#bundled-skills)
- Stock: when a project skill named `verify` or `simplify` exists, Claude Code's built-in commit instructions tell Claude to run it before each commit; `/run-skill-generator` and `/verify` record the project's build-and-launch recipe as a committed skill (https://code.claude.com/docs/en/skills#run-your-checks-before-each-commit)
- Stock: Claude Code ships "built-in instructions for how to write commits and pull requests" plus a git status snapshot in every conversation (https://code.claude.com/docs/en/settings-reference#includegitinstructions)
- Edge: a project kernel that loads in every chat for both tools (template `CLAUDE.md`, template `AGENTS.md`)
- Verdict: none — every Claude Code and Codex user already has this; it is the shoelaces.
- Edge: the template kernel ships a pre-written working agreement, not an empty file: inspect logs, run scripts and read code before claiming anything works; never claim a visual check you did not perform; when the authoritative check cannot run, flag the risk instead of claiming a pass; reproduce bugs before fixing; no unrequested features or abstractions; never hard-code to pass a test and say when a test is wrong; on "Complete" commit, push and open or update the one PR for the branch; squash-merge; never force-push; pressure-test weighty recommendations with `/why` (template `CLAUDE.md` § CRITICAL: Verification, § Core principles, § Git: push on completion)
- Verdict: thin — each rule is one sentence a user could write, the docs teach exactly this kind of rule, and stock covers parts (verify-before-commit skill, built-in git instructions); the gain is a curated, field-tested set on day one, not a mechanism. The two rules that do change outcomes (pitfalls, review before merge) are scored under lessons and cross-vendor.
- Edge: kernel structure: `CLAUDE.md` holds cross-cutting rules only, topical facts live in six on-demand reference files indexed by a table, a standing rule says new rules must earn their place, stale content gets pruned and nothing the harness already injects is restated (template `CLAUDE.md` § Core principles, § Project reference library; product.md § Layer 1: kernel and token efficiency)
- Verdict: thin — the stock docs give the same structure advice (under 200 lines, procedures to skills, area rules to path-scoped rules) and `/doctor` performs the migration; the firmware ships it already split and carries a rule that keeps it that way.
- Edge: `/init-project` fills the kernel's FILL IN sections from detected facts: what the project is plus a short "won't compromise on" list capped near 10 lines, what this sandbox can verify and which signal is authoritative, and the deploy, install and migration policy; it asks only for consequential facts it cannot detect (template `.claude/skills/init-project/SKILL.md`; template `CLAUDE.md` § What this project is)
- Verdict: thin — interactive `/init` (`CLAUDE_CODE_NEW_INIT=1`) already detects, asks about gaps and proposes before writing; the firmware's difference is which questions it asks (verification capability, won't-compromise list).
- Edge: "updates": the setup profiles say "A configured project can receive a requested narrow update"; nothing re-runs setup or rewrites rules on its own as the repo changes (template `.claude/skills/init-project/references/profiles.md` § Optional setup profiles and starter cleanup)
- Verdict: none — stock `/init` on an existing CLAUDE.md "suggests improvements rather than overwriting it"; the owner's phrase "automatically adds or updates these rules" overstates the skill, which adds on a setup request and updates only on a further request.
- Edge: `/init-project` also generates the project's own CI (`write-ci-workflow.mjs`: Node, Python, Rust, Go jobs plus a `firmware` job running the Codex skill sync check), offers a full or minimal skill profile, sets the prose default, strips template-only files and wires the `starter` remote (template `.claude/skills/init-project/references/ci.md`, `profiles.md`)
- Verdict: thin — no stock command writes a test CI workflow, but any session writes one on request; the gain is convenience plus an approval step.

## lessons

- Stock: auto memory is on by default; Claude "saves four kinds of notes for itself", including `feedback`: "corrections you give Claude and approaches you confirm", and the first 200 lines or 25KB of `MEMORY.md` load every session (https://code.claude.com/docs/en/memory#auto-memory)
- Stock: auto memory limits: "Claude skips anything it can derive from the codebase, such as architecture, file paths, or debugging fixes" and "Auto memory is machine-local ... Files are not shared across machines or cloud environments" (https://code.claude.com/docs/en/memory#auto-memory)
- Stock: memory files get a `modified` ISO timestamp so Claude and the user see how current a fact is; `/memory` browses and edits them; "add this to CLAUDE.md" writes the committed file instead (https://code.claude.com/docs/en/memory#how-it-works)
- Stock: Claude Code Projects (public beta, Pro and Max) keep project memory of "requirements, decisions, and pitfalls" that every cloud thread reads at start; "when you correct a thread, also tell Claude to remember the correction" (https://code.claude.com/docs/en/claude-projects#give-a-project-standing-context)
- Stock: Codex local memories are off by default, live in `~/.codex/memories/`, and the docs say: "Keep required team guidance in `AGENTS.md` or checked-in documentation. Treat memories as a helpful recall layer, not as the only source for rules that must always apply." (https://learn.chatgpt.com/docs/customization/memories)
- Stock: `/doctor prompt-audit` reports outdated or contradictory instructions across CLAUDE.md, rules and skills, changing nothing until asked (https://code.claude.com/docs/en/memory#audit-your-instruction-files)
- Edge: the pitfall rule: when a quirk cost a retry, a backed-out change or a user correction and its cause is confirmed, the agent writes it to the committed `.claude/reference/pitfalls.md` before the task ends, without asking, amending an existing entry over adding one (template `CLAUDE.md` § Project reference library; template `.claude/skills/recall/SKILL.md`)
- Verdict: strong — stock auto memory saves without asking but stays on one machine and skips debugging fixes, Projects memory and CLAUDE.md both need the user to say "remember"; here the lesson lands in git and reaches teammates, other machines, cloud sessions and Codex (it is an agent instruction, not enforced, and committing it follows normal git authorization).
- Edge: `recall` reads only the topic files a task needs and, when a stored fact changes an action, says so with file and date ("per pitfalls.md (2026-03-14): ..."), and prefers current source when a note conflicts with reality (template `.claude/skills/recall/SKILL.md`)
- Verdict: thin — stock memory topic files and path-scoped rules also load on demand, and memory files carry a `modified` date; the visible dated citation is a detail.
- Edge: save discipline: every non-pitfall fact needs the user's authorization and must change future decisions, be durable and carry evidence; a contradicted fact is amended in place with a `retired YYYY-MM-DD: <old claim>; reason: <what changed>` line; `memory-audit.mjs` lists never-read files and entries older than six months (template `.claude/skills/recall/SKILL.md`; product.md § Layer 2: project memory)
- Verdict: thin — `/doctor prompt-audit` and auto memory's own index pruning cover staleness; the retire line and audit script are finer-grained versions of that.

## two-tools

- Stock: Claude Code reads `AGENTS.md` directly, or a `CLAUDE.md` containing `@AGENTS.md` keeps "the one file every tool shares"; it does not read "anything under a `.agents/` directory" (https://code.claude.com/docs/en/memory#share-one-file-with-other-coding-tools)
- Stock: Codex reads `AGENTS.md` and can be pointed at other names with `project_doc_fallback_filenames` (https://learn.chatgpt.com/docs/agent-configuration/agents-md)
- Stock: each tool's learned memory is its own and local: Claude Code auto memory under `~/.claude/projects/<project>/memory/` (https://code.claude.com/docs/en/memory#storage-location), Codex memories under `~/.codex/memories/` (https://learn.chatgpt.com/docs/customization/memories)
- Stock: one-time migration exists both ways: Claude Code `/import codex` brings "instruction files, MCP servers, commands, subagents, and skills" (https://code.claude.com/docs/en/commands), and Codex `/import` brings Claude Code setup (https://learn.chatgpt.com/docs/developer-commands?surface=cli)
- Edge: one shared rule surface with a clean runtime boundary: `AGENTS.md` tells Codex to read only three `CLAUDE.md` sections (project identity, verification, environment) plus the reference files, never to run the Claude hook, to spawn fresh-context subagents, and to call `rtk` explicitly (template `AGENTS.md` § Defaults, § Capabilities, § RTK)
- Verdict: thin — stock already shares one instruction file between the tools; the firmware's split of shared facts from runtime-specific workflow is a detail.
- Edge: one lesson store for both tools: Claude Code and Codex both read and write `.claude/reference/` through `recall`, and both built-in memories are switched off (`autoMemoryEnabled: false`; "Do not use or enable Codex's built-in `memories` feature for project knowledge") so lessons never fork per tool (template `.claude/settings.json`; template `AGENTS.md` § Safety)
- Verdict: strong — in stock, a lesson Claude Code learns stays in Claude's machine-local memory and Codex never sees it (and the reverse); no stock feature carries a learned lesson from one tool to the other.

## planning

- Stock: plan mode: Claude "reads files, runs shell commands to explore, and writes a plan, but does not edit your source"; edits stay blocked until the user approves; `Ctrl+G` edits the plan; `/plan` enters it (https://code.claude.com/docs/en/permission-modes#analyze-before-you-edit-with-plan-mode)
- Stock: plan files are written to disk and `plansDirectory` chooses where (https://code.claude.com/docs/en/settings-reference#plansdirectory)
- Stock: `AskUserQuestion` "asks multiple-choice questions to gather requirements or clarify ambiguity" (https://code.claude.com/docs/en/tools-reference#askuserquestion-tool-behavior), and the best-practices page prescribes "Interview me in detail using the AskUserQuestion tool ... then write a complete spec to SPEC.md" (https://code.claude.com/docs/en/best-practices#let-claude-interview-you)
- Stock: Codex has `/plan`, and its long-running-work guide says "start with `/plan`. Ask ChatGPT to interview you, identify constraints, and turn the result into a goal with measurable success criteria" (https://learn.chatgpt.com/docs/long-running-work)
- Stock: the advisor tool consults a second, stronger Claude model "before committing to an approach"; it receives the full conversation (https://code.claude.com/docs/en/advisor)
- Edge: `deep-plan` interview discipline: rounds of at most 4 questions, recommendation first, ask only where a wrong guess forces rework (low-stakes items become recorded assumptions), never two questions in one round that depend on each other, a depends-on graph where a changed premise voids its descendants, and it never answers a decision for the user (template `.claude/skills/deep-plan/SKILL.md` § Building a round, § Handling answers)
- Verdict: thin — plan mode plus "interview me with AskUserQuestion" already gives a typical user an interview and a spec; the question discipline is a refinement.
- Edge: a resumable ledger at `.tmp/deep-plan/<slug>/ledger.md` with stable question IDs, the user's verbatim answers and rejected options, resumed after compaction or in a new session, with a 30-minute ownership check (template `.claude/skills/deep-plan/SKILL.md` § Ledger)
- Verdict: thin — stock plan files and the SPEC.md pattern already persist the plan; the decision ledger is a detail.
- Edge: before the Go gate, the 1 to 3 weightiest decisions go to `why`, one fresh reviewer that never saw the conversation, plus a "what would go wrong if reversed" question; nothing is built until the user picks Go (template `.claude/skills/deep-plan/SKILL.md` § Stop and gate; template `.claude/skills/why/SKILL.md`)
- Verdict: thin — stock plan approval already gates building and the advisor already gives a second opinion; the difference is that `why`'s reviewer starts without the conversation.

## long-work

- Stock: "Tasks persist across context compactions", and `CLAUDE_CODE_TASK_LIST_ID` shares one list across sessions (https://code.claude.com/docs/en/interactive-mode#task-list)
- Stock: `/goal` keeps Claude working across turns until a condition holds; Claude Code restores an active goal on every resume route (https://code.claude.com/docs/en/goal#resume-with-an-active-goal). Codex has its own `/goal` Goal mode (https://learn.chatgpt.com/docs/long-running-work)
- Stock: dynamic workflows run a script that orchestrates dozens to hundreds of subagents, "Resumable in the same session", for migrations and audits (https://code.claude.com/docs/en/workflows#when-to-use-a-workflow)
- Stock: Projects run "A build or migration bigger than a session" as parallel cloud threads with shared memory and an Overview of what needs you (https://code.claude.com/docs/en/claude-projects#when-to-use-a-project)
- Stock: project-root CLAUDE.md is re-read after `/compact`, and invoked skills are re-attached after auto-compaction within a token budget (https://code.claude.com/docs/en/context-window#what-survives-compaction)
- Edge: `long-horizon` keeps a state file on disk (contract with numbered acceptance checks, versioned amendments that never weaken acceptance, Verified progress, Remaining with depends-on, Method notes, Audit log) and resumes after compaction by reconciling it with the real workspace, asking before taking over a run another session touched in the last 30 minutes (template `.claude/skills/long-horizon/SKILL.md` § State file)
- Verdict: thin — the task list, `/goal` resume, resumable workflows and Projects already carry long work across compaction and sessions; persistence alone is not the edge.
- Edge: dead ends and stagnation rules: a failed approach is recorded and not retried without new evidence; the same step failing audit twice forces a new approach; three batches with nothing newly verified force a rewrite of the remaining plan; at max(5, 2 x initial steps) rounds the plan is reassessed; a plateau can be sent to Codex for a diagnosis from a different model family (template `.claude/skills/long-horizon/SKILL.md` § Stagnation, § Guardrails)
- Verdict: strong — `/goal` stops only when its evaluator says met or impossible, an unrecoverable error occurs, or Claude makes no tool calls for several turns; no stock feature remembers ruled-out approaches or forces a change of approach after repeated failure.
- Edge: parallel rounds, each in its own detached worktree with its own baseline, merged back only when the main file still matches its pre-checkout hash, then one fresh auditor reruns every applied round's check in the main workspace (template `.claude/skills/long-horizon/SKILL.md` § Parallel rounds)
- Verdict: thin — `/batch`, workflows and `isolation: worktree` subagents already run parallel units in isolated worktrees; conflict-by-hash and the post-merge recheck are details.

## checking

- Stock: `/goal` "adds a separate evaluator that checks your condition after every turn, so completion is decided by a fresh model rather than the one doing the work", but the evaluator "doesn't run commands or read files independently", judges "what Claude has surfaced in the conversation", and runs on the small fast model (https://code.claude.com/docs/en/goal#how-evaluation-works)
- Stock: the best-practices page prescribes "Before treating a task as done, have a subagent review the diff in a fresh context and report gaps", for example against PLAN.md (https://code.claude.com/docs/en/best-practices#add-an-adversarial-review-step)
- Stock: each subagent "runs in its own context window", and `isolation: worktree` gives it an isolated repository copy (https://code.claude.com/docs/en/sub-agents)
- Stock: workflows can "have independent agents adversarially review each other's findings before they're reported" (https://code.claude.com/docs/en/workflows#when-to-use-a-workflow); `/verify` builds and runs the app "without falling back to tests or type checks" (https://code.claude.com/docs/en/skills#run-and-verify-your-app)
- Stock: Stop hooks can run "a script for deterministic checks or a prompt for model-evaluated ones" after every turn (https://code.claude.com/docs/en/hooks-guide#prompt-based-hooks)
- Stock: Codex's guide asks you to "Write a goal that lets ChatGPT verify its own progress" (https://learn.chatgpt.com/docs/long-running-work)
- Edge: the `long-horizon` auditor is a fresh subagent whose brief is written at Plan, before the executor exists, saved with a recorded sha256 and dispatched unchanged; it never sees the executor's report or narrative, reruns the done-check itself, and treats executor logs as claims (template `.claude/skills/long-horizon/SKILL.md` § Context boundary, § Round loop)
- Verdict: strong — the `/goal` evaluator reads only the conversation and never runs anything, and the stock reviewer-subagent pattern gets its criteria from the same context that watched the work; no stock checker is pinned before the work starts and kept blind to the worker's account.
- Edge: integrity check by hash: before each round the manager records a content-hash manifest of the workspace; the auditor diffs against it and rates the round `suspect` when the executor touched anything outside its write scope or the tests and gates that judge it ("passing check proves nothing if executor could edit it") (template `.claude/skills/long-horizon/SKILL.md` § Round loop; template `.claude/skills/long-horizon/scripts/manifest.mjs`)
- Verdict: strong — no stock reviewer, evaluator or hook pattern checks whether the worker edited the check it was graded by.
- Edge: only results that are complete, clean and aligned with the current contract enter Verified progress, and a last fresh auditor reruns every acceptance check on the final workspace because a later round can break an earlier one (template `.claude/skills/long-horizon/SKILL.md` § Completion)
- Verdict: thin — a `/goal` condition is also re-judged at the end; the difference is who runs the final check (a fresh agent that runs it, not a model reading the transcript).

## attempts

- Stock: `/batch` decomposes a change into 5 to 30 independent units and runs one background subagent per unit in an isolated worktree; each "implements its unit, runs tests, and publishes its change" (https://code.claude.com/docs/en/commands)
- Stock: a fork subagent is the documented choice "when you want to try several approaches in parallel from the same starting point" (https://code.claude.com/docs/en/sub-agents#fork-the-current-conversation); `/branch` tries another direction in a copy of the conversation (https://code.claude.com/docs/en/commands)
- Stock: workflows can "draft a plan from several angles and weigh them against each other" (https://code.claude.com/docs/en/workflows#when-to-use-a-workflow); agent teams run "competing hypotheses" where teammates "try to disprove each other's theories" (https://code.claude.com/docs/en/agent-teams)
- Stock: Codex runs subagents in parallel and supports git worktrees (https://learn.chatgpt.com/docs/agent-configuration/subagents)
- Edge: `arena` builds 3 or more real candidates from different angles in isolated worktrees, has a fresh read-only judge score them blind against 3 to 6 pass/fail criteria an outsider could check (names, vendor and rationale stripped), picks the base the merges would disturb least and grafts one or two ideas from each other candidate; a split premise means the brief had a gap and gets one rerun (template `.claude/skills/arena/SKILL.md`)
- Verdict: thin — stock documents parallel attempts from one starting point and multi-angle drafting; blind judging and grafting are the difference in detail.
- Edge: mixed vendors without asking: when a Codex login exists, one candidate and the judge run through `codex exec` on the pinned Sol model, so another company's model both competes and judges (template `.claude/skills/arena/SKILL.md` § Workers)
- Verdict: strong — every stock parallel-attempt feature (`/batch`, forks, workflows, agent teams, advisor) runs Claude models only.

## merge

- Stock: Claude Code Review (GitHub app, Team and Enterprise, research preview) reviews on PR open, "After every push" or on request with a multi-agent fleet plus a verification step; findings "don't approve or block your PR" and its check run "always completes with a neutral conclusion so it never blocks merging"; to gate merges you parse the check output in your own CI; about $15-25 per review (https://code.claude.com/docs/en/code-review#how-reviews-work)
- Stock: `/code-review` reviews the current diff, a PR, branch or path in a background subagent; `--fix` applies findings, `--comment` posts them; `ultra` runs ultrareview in the cloud, where "every reported finding is independently reproduced and verified" (https://code.claude.com/docs/en/code-review#review-a-diff-locally, https://code.claude.com/docs/en/ultrareview)
- Stock: auto-fix (`/autofix-pr`) watches a PR and, "when a check fails or a reviewer leaves a comment, Claude investigates and pushes a fix if one is clear" (https://code.claude.com/docs/en/claude-code-on-the-web#auto-fix-pull-requests)
- Stock: Codex reviews GitHub PRs on `@codex review` or automatically once **Automatic review** is on, flags "only P0 and P1 issues", fixes on `@codex fix the P1 issue`, and "Code review rules guide Codex; they don't replace tests, branch protections, or required approvals" (https://learn.chatgpt.com/docs/third-party/github)
- Stock: `codex review` runs a non-interactive review of uncommitted changes, a base-branch diff, a commit or custom instructions; `/review` reviews the working tree in the TUI (https://learn.chatgpt.com/docs/developer-commands?surface=cli)
- Edge: `/merge`: the user types it once and merge mode covers every PR the session opens or updates; per PR one `codex-fullreview` (it must spawn at least one sub-reviewer to count), confirmed blocking and should-fix findings fixed in one commit, then `codex-review` alone on the full PR diff at the new head, at most 3 reruns; then every PR check (an absent or skipped required check is not a pass); then `gh pr merge --squash --match-head-commit <verified head>`; if the head moved the verdict is void; past the cap the PR is left open as `blocked` (template `.claude/skills/merge/SKILL.md`)
- Verdict: thin — a Team or Enterprise user can assemble most of this from stock parts (Code Review on every push, a CI job that fails on Important findings, auto-fix, GitHub auto-merge); what stock lacks is the rerun cap, the binding of the review verdict to the exact merged commit, and running on a subscription with no CI scripting.
- Edge: a person approves every merge: `/merge` runs only when the user types it and is never self-started, the user can turn merge mode off at any time, and `babysit-ci` never merges (template `.claude/skills/merge/SKILL.md` § Merge mode; product.md § Layer 6: human approval)
- Verdict: none — stock reviewers never merge either; this is a property the film must state, not an advantage over stock.
- Edge: for a PR that changes flows, boundaries, data model or state, `/merge` puts a short Mermaid diagram in the PR description and the same diagram in `.claude/reference/architecture.md`, so the owner reads the diagram instead of the diff (template `.claude/skills/merge/SKILL.md` § Step 1: Integrate)
- Verdict: thin — no stock feature does this, but it is a prompt-level convention any session follows on request.

## learning

- Stock: `/insights` analyzes up to 200 recent sessions on this machine and writes an HTML report covering "friction points such as misunderstood requests or buggy code, and suggestions"; it is not available in cloud sessions and applies nothing (https://code.claude.com/docs/en/costs#analyze-your-usage-patterns)
- Stock: auto memory learns from corrections across sessions without being asked (https://code.claude.com/docs/en/memory#auto-memory); `/skill-doctor` lists never-used skills and their context cost (https://code.claude.com/docs/en/skills#find-unused-skills)
- Stock: routines run a prompt on a schedule, on API calls or on GitHub events in the cloud (https://code.claude.com/docs/en/routines); `/loop` and desktop scheduled tasks repeat prompts (https://code.claude.com/docs/en/scheduled-tasks)
- Stock: improvements spread across projects through plugins and marketplaces (https://code.claude.com/docs/en/plugins/overview), user-level rules and symlinked `.claude/rules/` (https://code.claude.com/docs/en/memory#share-rules-across-projects-with-symlinks)
- Edge: `/refine weekly` runs unattended, reads the last 7 days of this repository's sessions, counts correction turns and the user's PR comments per merged PR, appends a dated metrics row and compares it with the previous four, flags any task asked in three or more sessions as a skill candidate, edits only what passes its evidence gate, and opens one PR on a fresh branch; it never merges (template `.claude/skills/refine/SKILL.md` § Weekly mode)
- Verdict: strong — `/insights` reports friction but changes nothing, keeps no trend and is local-only, and auto memory stores corrections as private notes; no stock feature turns a week of corrections into a reviewed rule or skill change to the repository.
- Edge: the evidence gate: only the user's own words count as a preference (a table: "said it applies from now on" saves, "let it pass several times" is only suggested, "only the agent did it" is nothing); a failure fix must pass three checks (caused by an instruction, tool or config; causal link stated; the changed rule was active), else zero changes; each change goes to exactly one home (template `.claude/skills/refine/SKILL.md`)
- Verdict: thin — stock has no such gate, but auto memory and `/doctor prompt-audit` already cover capturing corrections and pruning bad instructions; the gate is quality control on that.
- Edge: lessons travel between repos: `sync-starter` Direction B genericizes a fix and opens a template PR, Direction A pulls chosen shared paths into other projects, and the SessionStart hook checks template drift at most weekly and suggests `/sync-starter` (template `.claude/skills/sync-starter/SKILL.md`; template `.claude/hooks/session-start.sh`)
